SETUP — AI Workspace Initialization

One-time product foundation setup. Done once, benefits every module forever.
PM Input System
⏱ 60–90 min (once) ▼
STEP 0.1 Create AI Project Workspace 👤 PM
Create a dedicated Claude Project (or equivalent persistent workspace) for the product. This is the container for all persistent context.
  • Tool: Claude Projects, ChatGPT Projects, or any AI with persistent memory
  • Naming: [ProductName] — PRD Engine v1
  • System Prompt: Set role as "Senior Technical PM" with output format expectations
  • Access: Single workspace per product — PM owns it, team gets read access
STEP 0.2 Upload Product Foundation Documents 🧠 Context
Upload the core product knowledge base. These documents define the AI's understanding of your product and never need re-uploading unless updated.
📋
Product Brief (1–2 pages)
  • Vision, mission, core value props
  • Target market and user segments
  • Key differentiators vs competitors
  • Current product stage (MVP/growth/scale)
🏗️
Architecture Overview
  • Tech stack (frontend, backend, DB, cloud)
  • Microservices map with module names
  • Auth system and session model
  • Third-party integrations list
👥
Personas Master Doc
  • All user roles across the product
  • Permission levels per role
  • Primary use cases per persona
  • Platform preferences (web/mobile)
STEP 0.3 Establish PRD Template & Conventions 🧠 Standards
Define the output standards before generating any PRD. Consistency starts here.
  • PRD Template: Upload or define your 10-section template structure with exact headings
  • FR-ID Scheme: Define numbering format — e.g., FR-[MODULE]-[SEQ]
  • Error Message Convention: Define inline | toast | modal rules upfront
  • API Convention: Define endpoint format — e.g., POST /api/v1/{module}/{action}
  • AC Format: Checkbox format? Gherkin? Decide now and lock it in
  • Validation Test: Generate a small sample section to confirm AI outputs match your template

DEFINE — Product Thinking

PM identifies module, personas, flows, data, and constraints before touching AI
PM Only
⏱ 15–30 min ▼
STEP 1.1 Identify Module & Business Purpose 👤 PM
Define what this module does, why it exists, and where it fits in the product architecture.
  • Problem Statement: What user/business problem does this solve?
  • Product Fit: Where does this sit in the module hierarchy? (e.g., Auth → Login)
  • Business Case: Revenue impact, compliance requirement, or user retention driver?
  • Scope Flag: Is this MVP or Future Phase?
  • Dependencies: What existing modules does this interact with?
STEP 1.2 Define User Personas & Access Context 👤 PM
Identify every persona that touches this module and their distinct needs.
AttributeDetail RequiredExample
Persona NameRole-based identifierCustomer, Admin, Agent
Primary GoalWhat they want to accomplish"Reset password without calling support"
Pain PointsCurrent frustrations"Too many steps to verify identity"
Access LevelPermission boundariesread-only, full-CRUD, approve-only
PlatformWhere they interactWeb, Mobile, Both
FrequencyHow often they use thisDaily, Monthly, One-time
STEP 1.3 Map Core User Flows 👤 PM
Trace every path a user takes — happy path, alternative paths, and error exits.
  • Happy Path: Ideal journey from entry → success (e.g., Login → OTP → Dashboard)
  • Alternative Paths: Biometric login, SSO, remember-me flows
  • Error Paths: Wrong password, locked account, expired OTP, network timeout
  • Edge Cases: Multi-account user, concurrent sessions, mid-flow abandonment
  • Entry Points: Where users arrive from (deep link, redirect, manual navigation)
  • Exit Points: Where users go after completion (dashboard, next step, logout)
  • Cross-Module Handoffs: e.g., Login success → triggers Profile module → loads Dashboard
STEP 1.4 Define Data Fields & Business Rules 👤 PM
Specify every data element with type, constraints, and validation logic.
FieldTypeConstraintsValidation Rule
EmailstringRequired, max 254 charsRFC 5322 format, domain MX check
PasswordstringMin 8, max 128 chars1 upper, 1 lower, 1 digit, 1 special
OTPstringExactly 6 digitsNumeric only, expires in 120s
PhonestringE.164 formatCountry code + 10-15 digits
  • Business Rules: Max 5 OTP attempts → 15-min lockout → escalate to support
  • Security: Passwords hashed with bcrypt, OTP via SMS/email, session JWT with 30-min expiry
  • Compliance: GDPR data retention, PCI-DSS for payment fields, audit log requirements
STEP 1.5 Attach Design References & Wireframes 👤 PM
Link all visual references that inform the PRD's UI/UX section.
  • Figma Links: Wireframes, high-fidelity mockups, prototypes
  • UI States: Note which screens need loading, empty, error, success states
  • Design Patterns: Reference existing module patterns for consistency
  • Responsive: Note breakpoints and mobile-specific layouts

STEP 3.0 Outline-First (Optional but Recommended) 👤 PM + 🤖 AI
Before full PRD generation, ask AI to produce a section outline only. PM validates structure in 2 minutes — saves a full iteration round.
  • Prompt: "Generate only the section headings and sub-headings for this PRD — no content yet"

  • Approve or adjust: Add/remove sections before the heavy generation pass
  • Then prompt: "Now fill in complete content for all sections following this outline"
  • Time saved: Catching a missing section at outline stage takes 2 min vs 30 min after full generation

ITERATE — Review, Flag, Refine

PM reviews for business accuracy, flags gaps, AI refines targeted sections
PM Reviews AI Refines
⏱ 30–60 min (2–3 rounds) ▼
STEP 4.1 PM Deep Review — Quality Gate 👤 PM
Systematic review against 8-point quality checklist. This is the critical human judgment step.
  • Dev Ready: Could a developer build this without asking a single question?
  • Data Complete: Every field has type, constraint, validation rule, and error message?
  • States Covered: Does every screen define loading, empty, error, and success states?
  • Errors Specific: Are error messages specific with display type (inline/toast/modal)?
  • Security Consistent: Do security configs match patterns from prior modules?
  • API Realistic: Are endpoint paths and methods correct for the tech stack?
  • Edge Cases: Are boundary conditions and concurrent access scenarios covered?
  • Cross-Module: Do references to other modules accurately reflect their current PRDs?
GATE Quality Decision: Gaps Found? ⚖️ Decision
PM evaluates if the generated PRD meets production-ready standards.
⚠ GAPS FOUND → Refine
PM provides targeted, specific feedback. Examples:
  • "Add multi-account selection step between lookup and OTP"
  • "Field X needs max 50 characters, not 100"
  • "Missing error state for network timeout on OTP screen"
  • "OTP cooldown should be 60s not 30s"
  • "Add concurrent session detection for mobile + web"
✅ APPROVED → Proceed
PRD passes all 8 quality checks:
  • All edge cases comprehensively covered
  • Consistent with prior module patterns
  • Developer-ready with zero ambiguity
  • QA can write test cases directly from AC
  • → Proceed to Phase 5: QA Align
STEP 4.3 AI Refines Targeted Sections 🤖 AI
AI processes PM feedback and updates only the flagged sections while maintaining cross-section consistency.
  • Surgical Updates: Only modifies sections PM flagged — not full regeneration
  • Cascade Awareness: If a field changes, updates AC, FR table, UI spec, and tech notes
  • Pattern Preservation: Maintains formatting, numbering, and convention consistency
  • Version Tracking: Notes what changed for the change log section
🔁
Iteration Loop: 2–3 Rounds Typical
Round 1: Major gaps • Round 2: Fine-tuning • Round 3: Polish (if needed)

QA documents are hyperlinked from PRD Section 9, creating traceability from user story → acceptance criteria → test case.
  • Traceability: US-001 → AC-001-01 to AC-001-35 → TC-001-01 to TC-001-35
  • Separation: PRD stays readable for stakeholders; QA gets atomic-level detail
  • Immediate Use: QA team can start writing automation scripts from day 1 of dev
STEP 5.3 QA Team Review & Validation 👥 Team
QA lead validates test coverage completeness and confirms all scenarios are testable.
  • Validates coverage against each user story
  • Flags untestable criteria for PM clarification
  • Identifies missing integration test scenarios
  • Confirms environment requirements for test execution
STEP 5.4 Developer Technical Review 👨‍💻 Dev Lead
Tech lead or senior developer reviews the PRD before development begins. This is the last checkpoint for catching technical ambiguity before it becomes a sprint blocker.
  • API Feasibility: Are the proposed endpoints consistent with existing architecture?
  • Data Model: Do field definitions align with the actual DB schema?
  • Performance Flags: Are there any requirements that would cause N+1 queries or expensive operations?
  • Security Review: Does the security model align with existing auth patterns?
  • Missing Tech Notes: Any edge cases the PM missed that are obvious from a dev perspective?
  • Output: Dev lead adds technical notes section or flags items back to PM for v1.1

⚠️ What AI Cannot Replace — The PM's Irreplaceable Role

🎯 Product Vision
AI cannot define what to build, why it matters, or how it fits the company strategy. Vision is purely human.
👥 User Research
AI cannot interview users, observe behavior, synthesize qualitative insights, or feel user frustration.
⚖️ Prioritization Judgment
AI cannot weigh business context, political dynamics, resource constraints, or market timing for trade-offs.
🤝 Stakeholder Alignment
AI cannot negotiate, build consensus, manage expectations, or navigate organizational politics.
🧠 Domain Expertise
AI needs human validation for domain-specific business logic, regulatory requirements, and industry nuances.
🔍 Quality Gate Ownership
AI generates content but cannot self-evaluate business correctness. The PM is the final quality gate.

The PM doesn't write the documentation - they architect the thinking.
